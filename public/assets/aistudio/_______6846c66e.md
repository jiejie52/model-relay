**Relay 9.0.0 Context Continuation 改造技术方案**

**第一章：现有架构与代码差距分析**

**1.1 现有四层架构基线与核心不变量盘点**

对照《model-relay-9.0.0_架构机制说明_20261114.pdf》与 relay-9.0.0-context-continuation-slim 的 30 份源码及清单文件，当前 Relay 9.0.0 已建立\*\*控制面（Control Plane）→ 执行面（Execution Plane）→ 运行时（Runtime）→ 协议适配层（Protocol Adapter & Factory）\*\*四层单向不可变契约链路：

1.  **统一身份与双层恢复基线（已有能力）**：以 Session 冻结路由、账号作用域（account_scope_id）、连接指纹（connection_spec_hash）与能力/协议/缓存合同；以 Request 作为同步（InlineScheduler）与异步（QueueScheduler + relay_jobs）共用的唯一调用事实身份；通过 provider_dispatch_state（not_sent → dispatch_started → result_stored → committed）与三重围栏（数据库 ExecutionFence、应用层心跳联动取消、工厂级 TransportGuard）严守不可逆派发边界。

2.  **上下文与材料账本基线（已有能力）**：Session 级 context_policy（默认 conversation + cumulative）与 Request 级临时覆盖（conversation / explicit / session_materials_only）已实现读写解耦——Request 级策略仅裁剪本轮模型可见视图，不改变 ResultCommitter 向 relay_sessions 追加累计历史的提交规则；材料发生由 EffectiveMaterialPlacementPlan（material-placement/2）与 relay_sessions.committed_material_ledger、运行时 verify_and_pin_historical 及 sql/014_provider_binding_state_contract.sql 共同校验 binding_generation、生命周期状态与剩余安全有效期。

3.  **两阶段缓存治理基线（已有能力）**：缓存控制已拆分为执行面纯函数逻辑规划（CacheIntentPlan）与运行时只读仲裁及资源物化（CacheExecutionBinding），明确了“执行面不读实时库存、不污染 request_hash，运行时在 not_sent 物化并在 AtomicDispatchSealer 封存”的范式。

然而，在\*\*跨轮上下文状态续接（Context Continuation）\*\*维度上，当前系统完全处于无状态重放（Stateless Replay）或显式缓存切片（CachedContent）模式，尚不具备将上游原生状态句柄（如官方 Gemini Interactions API 的 previous_interaction_id、OpenAI/Grok Responses API 的 previous_response_id）纳入受治理一等公民的机制。

**1.2 逐层现有能力与结构差距深度分析**

**1.2.1 控制面（app/control_plane/\*、config/\*）**

- **已有能力**：

  - app/control_plane/definitions.py 定义了 CapabilityContract、ProtocolProfileSpec、CachePolicySpec 与 ModelOffering（即文档中的 Model Supply），支持离线编译并输出哈希锁定的只读配置；CONTROL_PLANE_SCHEMA_VERSION = "relay-model-control-plane/3.0"。

  - config/google_official.declaration.json 已登记 gemini_google_official_prod 连接，绑定 protocol: "gemini_native" 与 supported_mechanisms: \["stateful_resource", "implicit_prefix"\]。

- **结构差距**：

  1.  **缺少续接能力子合同与续接策略对象（需新增/扩展）**：CapabilityContract 仅有 cache 字典，无 continuation 能力声明，无法刻画上游状态引用属于不可变树状锚点（immutable_tree_anchor）、受限线性游标（linear_ephemeral_cursor）还是可变会话容器（mutable_session_container），亦无远端保留时长（如 Gemini Interactions 付费层 55 天 vs 免费层 1 天）与 ZDR（零数据保留）约束字段；同时缺少与 CachePolicySpec 对称的 ContinuationPolicySpec（如 continuation_mode="prefer_stateful_anchor"）及 ModelOffering.continuation_policy_id 关联字段。

  2.  **缺少 Interactions 协议族注册与显式缓存互斥门禁（需扩展）**：app/control_plane/definitions.py（第 746–755 行）连接协议白名单仅允许 {"responses", "chat_completions", "claude_messages", "gemini_native", "moonshot_chat"}，未纳入 "gemini_interactions"（或在 Gemini 协议配置下区分 generateContent 与 interactions Wire 形态）；编译器尚无“启用 Gemini Interactions 状态续接时强制关闭 stateful_resource（显式 CachedContent）”的跨合同自洽校验。

**第二章：完整改造架构及数据结构设计**

**2.1 端到端数据流与三层核心职责分离边界**

本次改造严守 Relay 9.0.0“**逻辑计划在执行面先冻结、物理绑定在运行时后落实、发送前原子封存建立不可逆门槛、历史与锚点在提交段原子生效**”的铁律，绝不绕开现有架构另建旁路。调用方接口保持**零侵入**（Session 默认仍为 context_policy="conversation"、history_mode="cumulative"），上下文三域概念严格正交解耦：

- **Context Storage（唯一权威存储）**：由 relay_sessions（history_version、history_object_id、committed_material_ledger）与 Object Storage 持久化的 transport_history 构成。**Anchor Ledger 只存锚点引用与覆盖证明摘要，绝不另存第二份历史副本**。

- **ContextPlan（协议无关的完整语义投影）**：执行面 ContextPlanner 仅依据 context_policy 与 Context Storage 输出本轮模型**逻辑上应当看到的完整上下文全集**（完整有效指令、工具、可见历史序列、有效材料）及分段前缀指纹链。**严禁在执行面为迁就增量续接而裁剪 ContextPlan 的可见历史或材料清单**。

- **Context Continuation & Context Caching（物理传输收敛与缓存协同）**：状态续接将网络传输收敛为“已提交父锚点引用 + 未覆盖增量轮次（Multi-turn Delta）+ 当轮新增输入 + 当轮独立控制块”；缓存体系继续区分 Explicit CachedContent、Relay Stable Prefix 与 Provider Implicit Cache (Observed)，通过控制面合同与状态续接协同或互斥。

**三层职责硬隔离红线**：

1.  **context_planner.py + continuation_intent_planner.py（执行面）**：只做确定性语义投影与合同资格规划，不查数据库活跃锚点表，不生成或感知任何上游 interaction_id。

2.  **physical_context.py + continuation_binder.py（运行时只读绑定）**：消费已验证的材料快照与锚点账本完成最长祖先寻优与降级裁决，构造 ContinuationExecutionBinding，不直接开启派发事务，也不拼装最终 HTTP 字节。

3.  **dispatch_sealer.py（运行时封存门槛）**：在单个 Postgres 事务中对 MaterialBinding、CacheExecutionBinding、ContinuationExecutionBinding 与 ExecutionFence 做最终一致性锁闭与 seal_hash 签名；一旦封存完成进入 dispatch_started，任何组件严禁剥离锚点重发。

**三类正交续接能力合同的核心语义约束**：

1.  **immutable_tree_anchor（默认最高优先级）**：上游每次成功调用产出一个内容不可变的快照节点 ID（如 previous_interaction_id、previous_response_id）。支持 supports_branching=True 与 supports_multiturn_delta=True：即使中间穿插了 explicit 轮次、失败轮次或指令微调分支，后续请求仍可从账本中任意合法历史祖先节点安全分叉，并通过 Multi-turn Delta 补齐中间未覆盖的可见历史轮次。

2.  **linear_ephemeral_cursor（受限线性游标）**：声明 supports_branching=False（且通常 supports_multiturn_delta=False）。仅当候选游标恰好由本 Session **紧邻上一轮已提交请求**（covered_end_turn_index == visible_turn_count - 1）产出、无任何中间穿插的 explicit / session_materials_only 改写轮次、且头部指纹完全一致时才允许续接；一旦线性连续性被破坏，必须在 not_sent 淘汰旧游标并回退为 Stateless 全量发送。

3.  **mutable_session_container（可变会话容器）**：远端维护可变会话对象（如部分厂商 Assistants Thread）。因其存在**写放大与并发/中断状态污染风险**（一旦 dispatch_started 后进入 indeterminate，远端容器内部历史长度已不可知），合同强制要求：① supports_branching=False；② 只要会话出现过任何 explicit / session_materials_only 请求或存在未对账的 indeterminate 记录，当前容器立即封存停用，只有在协议支持创建全新容器并注入完整前缀时才可重开，否则回退无容器全量路径。

**锚点状态机（仅允许单向收敛）**：

- **不存在 provisional 可选状态**：上游返回 2xx 时，候选锚点信息仅暂存于 execution-fact.json 归档对象中，此时在 relay_continuation_anchors 表中**不存在任何活跃记录**，后续请求绝不可能读到未提交历史的锚点。

- **active**：仅在 ResultCommitter 调用原子提交 RPC 成功推进 relay_sessions 历史版本时，同事务插入为 active。

- **superseded**：对 linear_ephemeral_cursor 模式，当新轮次产出了更新的线性游标或发生了 Stateless 重置时，旧游标更新为 superseded。

- **expired**：运行时 ContinuationBinder 在 not_sent 阶段按壁钟与 anchor_safety_margin_seconds 检测到过期时标记（或查询过滤）。

**2.6 工程落地关键边界补充（结合架构文档与源码的 4 项补充设计）**

1.  **零数据保留（ZDR）与 store=True 的安全合规门禁**：Gemini Interactions API 与 OpenAI Responses API 的锚点续接均依赖服务端持久化（store=True）。在控制面 CapabilityContract 与租户策略校验中补充规则：凡连接或租户开启 zero_data_retention=True 时，离线编译器与会话准入器强制将 effective_continuation_mode 锁死为 "off" 并对 require_stateful_anchor 执行 Fail-Closed（CONTINUATION_FORBIDDEN_BY_ZDR_POLICY），杜绝将 requested_cache_mode=off 误当作 ZDR 开关的同时守住隐私红线。

2.  **Gemini Files API（48h）与 Interactions API（付费 55 天 / 免费 1 天）的生命周期非对称收敛**：官方 Gemini Files API 上传的 fileUri 有效期仅为 48 小时，远短于付费层 interaction_id 的 55 天保留期。若第 50 小时仍复用含 fileUri 的旧 interaction_id，将在跨过 dispatch_started 后触发上游文件读取失败。为此补充硬规则：**锚点入库时的 expires_at 取 min(now + retention_ttl_seconds, min(covered_file_binding.expires_at))**；一旦底层文件绑定逼近 48h 到期，锚点在 not_sent 提前平滑退役。

3.  **聚合网关 Session Affinity 代次联动淘汰**：依据架构文档 11.7 节，聚合渠道启用 affinity_policy.enabled=True 时，PhysicalContextProjector.prepare_scope() 可能因漂移触发 rotate_affinity() 推进 affinity_epoch。对于 ContinuationPolicySpec.invalidate_on_affinity_rotation=True（尤其是网关 linear_ephemeral_cursor），ContinuationBinder 强制要求候选锚点的 affinity_epoch == state.wire\["affinity_epoch"\]；官方直连渠道（如 Google 官方 Gemini）affinity_policy.enabled=False，affinity_epoch 为空，安全旁路。

4.  **三维输入 Token 用量观测解耦（防止缓存命中率虚报或漏报）**：启用状态续接后，HTTP 实际上传字节仅包含增量轮次，但上游 usage 返回的 prompt_tokens_total 包含服务端从父锚点装载的历史 Token，且命中的 Google 内部隐式前缀缓存体现在 cached_tokens 中。在 usage_normalizer.py 与 compact_result 中新增 continuation_usage 独立统计维度：relay_omitted_history_estimated_tokens（Relay 侧省去重复序列化上传的估算 Token）、upstream_total_input_tokens（上游总计费输入基准）与 upstream_implicit_cached_tokens（上游实测隐式缓存折扣 Token），严禁把省传的报文体积伪造成“上游免计费 Token”。

**4.1 Gemini Interactions 轨道与显式 CachedContent 的控制面互斥与隐式缓存协同**

1.  **会话级控制面一次冻结互斥**：

    - cache.supported_mechanisms = \["implicit_prefix"\]（彻底移除 "stateful_resource"）；

2.  **previous_interaction_id 路由亲和红利与“零承诺”设计边界**：  
    在 Interactions API 中携带合法 previous_interaction_id 时，Google 服务端基础设施会优先将请求路由至处理上一轮 Interaction 的计算节点，从而大幅提升服务端 KV Cache（Implicit Prefix Cache）的物理命中率并获得缓存 Token 计费折扣。但 Relay 在架构上坚守两项原则：

    - **不依赖“必然路由到同一服务器”的正确性假设**：即使 Google 内部因实例扩缩容将请求调度至新节点，服务端也会从持久化 Interaction 存储中完整加载父链上下文，语义正确性 100% 不受影响；

    - **不承诺缓存命中率**：隐式缓存命中始终作为 observed 事实从响应 usage 中忠实读取，绝不在执行面预扣费或伪造命中。

**第五章：Anchor Ledger 与历史原子提交机制**

**5.1 为什么“上游返回 2xx”绝不等于“续接锚点生效”**

在分布式模型中继系统中，“上游 HTTP 200 返回了 interaction_id”与“该 interaction_id 已成为后续请求可安全引用的会话历史锚点”之间横亘着四道后置门禁（见 app/execution_plane/result_committer.py 第 40–160 行）：

1.  **归档与租约围栏门禁**：Worker 可能在收到 200 后、写入 result_stored 前失租崩溃，或被新 epoch 抢占；

2.  **上游通用执行授权门禁（validate_execution_observations）**：聚合网关若发生了未经授权的模型降级替换或免费转付费兜底，Relay 会将该次请求判定为合同违约 failed，**不追加 Session 历史**；

3.  **思考执行合同门禁（verify_thinking_execution_contract）**：如硬约束 policy=require 下发生思考模式降级，或明确请求 OFF 时上游仍吐出思考块，判定为 failed，**不追加 Session 历史**；

4.  **Canonical JSON Schema 后置校验门禁（validate_against_schema）**：若模型输出的 JSON 违反调用方 Schema，请求同样转为 failed，**不推进 history_version**。

如果在上游返回 200 时就提前将 interaction_id 写入锚点账本，一旦上述任一后置校验拒绝提交，Session 权威历史仍停留在版本

，而账本中的 interaction_id 却包含了被废弃的脏轮次

，将导致后续所有对话被废案输出永久污染！因此，**续接锚点必须且只能在 ResultCommitter 完成全部后置门禁、随 Session 历史推进的同一个 PostgreSQL 事务中原子生效**。

**5.2 覆盖范围三重密码学证明（超越单一 history_version）**

正如第二章与第四章所证，在允许 Request 级 context_policy（explicit / session_materials_only）穿插的 cumulative Session 中，history_version 仅代表“该请求提交时会话总历史推进到了第几版”，**单凭 history_version 根本无法证明该锚点内部实际包含了哪几轮对话和哪一代材料绑定**。

因此，每个入账锚点必须携带不可伪造的**三重覆盖范围证明**：

1.  **版本与连续区间证明**：committed_history_version = V + 1、is_root_prefix = True、covered_turn_count = N + 1（对应提交前可见历史

加上本轮新增提交的第

轮，明确证明其连续覆盖有序历史区间

，绝无中间跳轮）；

2.  **头部与有序轮次链证明**：parent_head_fingerprint（证明固定指令与工具集）+ covered_turn_chain_hash（由提交前 turn_prefix_chain\[N-1\] 与本轮刚冻结的 new_history\[N\] 递推算出的第

阶链式哈希，当下一轮 ContextPlanner 重算 turn_prefix_chain 时，唯有字节级等价才能对上该哈希）；

3.  **材料发生与 Binding Generation 证明**：covered_material_bindings（合并父锚点已覆盖材料绑定 + Multi-turn Delta 轮次材料绑定 + 本轮新增 committed_occurrences 的 material_id、provider_binding_id、binding_generation、part_digest）及其整体摘要 covered_materials_digest。

**第六章：失败恢复、并发控制及兼容性设计**

**6.1 严守 not_sent 与 dispatch_started 不可逆派发门槛**

1.  **派发前（not_sent 阶段）封存前无损降级机制**：  
    在跨过 AtomicDispatchSealer 之前，尚未向上游发生任何模型推理副作用。此时若 ContinuationBinder 发现：

    - 候选父锚点已过期（expires_at \<= now + anchor_safety_margin_seconds）或已被标记为 invalidated / superseded：绑定器自动跳过该锚点，尝试回溯同一分支更早的合法祖先锚点；若无任何有效祖先，则在 allow_stateless_fallback=True 下无损降级为 stateful_root_init / stateless_full_replay（全量发送完整可见历史），业务调用零感知、零中断。

    - 候选父锚点覆盖材料的 binding_generation 与当前活跃绑定失配：绑定器立即以 ANCHOR_MATERIAL_GENERATION_MISMATCH 剔除该父锚点并回退至无锚点路径，绝不让旧代次文件句柄借由父锚点静默生效。随后：若本轮无需继承旧历史原生 URI（如 session_materials_only、explicit 或内联字节表示），请求使用新代次绑定正常完成无损调用；若已提交累计历史的冻结 transport_history 自身持有已过期或代次失配的原生 fileUri（material-placement/2），则由 verify_and_pin_historical 与 seal_materials_and_dispatch_v90 在 not_sent 阶段确定性按 HISTORICAL_MATERIAL_BINDING_EXPIRED Fail-Closed 拦截，绝不带病闯入 dispatch_started。

2.  **派发后（dispatch_started 阶段）严禁当轮剥离重发与次轮自愈重开机制**：  
    一旦 AtomicDispatchSealer 写入 dispatch_started，即跨过不可逆派发门槛。此时若上游返回锚点失效/过期/不存在（如 Gemini Interactions 返回 404 NOT_FOUND 或 400 无效 previous_interaction_id）：

    - **绝对禁止**在 Adapter 或 Runtime 内部私自删掉 previous_interaction_id 自动重发第二次推理请求；

    - RawErrorRecorder 原样归档上游完整原始错误字节（raw-error.bin + body_base64），ResultCommitter.fail_fact 将本轮 Request 置为确定性 failed、释放 relay_sessions.active_request_id 与 pins，并调用 invalidate_continuation_anchor_v90 将该失效父锚点标记为 status='invalidated'；

    - 当调用方发起**下一轮新 Request**（新 Idempotency-Key）时，ContinuationBinder 自动忽略已 invalidated 的锚点，回退至更早有效祖先或全量上下文发起新链调用，并在成功后登记全新根锚点，实现确定性跨轮自愈。

**6.2 indeterminate 未知状态锚点隔离与 result_stored 只提交恢复**

1.  **indeterminate 状态隔离**：若请求在 dispatch_started 后因失租、Worker 崩溃或流读取中断（stream_interrupted=True）进入 indeterminate：

    - 本轮即使上游实际已生成某个新 interaction_id，由于未完成归档与历史原子提交，账本中**绝不会产生新锚点**；

    - 其所引用的父锚点 relay_anchor_pins 转为 held 持续锁定保护；对 immutable_tree_anchor（Gemini / OpenAI），父锚点本身不可变、未被污染；而对 mutable_session_container，一旦出现 indeterminate 记录，原可变容器立即永久封禁，后续若人工解除 Session 占用也必须重开新容器或走 Stateless。

2.  **result_stored 只提交恢复幂等落盘**：当运行时已将 2xx 响应及 execution-fact.json（内含 continuation_binding 与上游 response_id）归档并推进至 result_stored、仅在最终数据库提交前中断时：无论是同步路径以原 Idempotency-Key 重放 POST（走 commit-only fence），还是异步 Worker 重新 claim 该 result_stored Job，均直接进入 ResultCommitter.recover_and_commit()，完全旁路运行时与协议适配层，从 execution-fact.json 精确重建 committed_anchor_record 并通过 complete_relay_request_v90（含 on conflict (source_request_id) do nothing 幂等保护）将历史与新锚点原子提交落盘。

**6.3 并发控制与串行多轮切换 context_policy 分支树演进**

1.  **三重防写偏并发控制**：

    - **受理互斥**：accept_relay_request 锁定 relay_sessions 行，校验 active_request_id is null（非空且非同幂等键则直接返回 SESSION_BUSY），从入口保证同一 Session 同一时刻最多只有一个活动 Request 正在规划、绑定或推进历史。

    - **提交乐观锁 + 执行围栏**：complete_relay_request_v90 同时核验 active_request_id = p_request_id、history_version = p_expected_history_version 与 validate_request_execution_fence_v71（校验活跃 owner、epoch 与数据库壁钟 clock_timestamp()），彻底杜绝僵尸进程或过期 Worker 写入陈旧锚点导致账本写偏（Write Skew）。

2.  **串行切换 context_policy 与指令调整时的分支树演进**：  
    在同一 Session 内串行多轮动态切换 conversation → explicit → session_materials_only → conversation 或切换不同阶段 instructions 时，relay_continuation_anchors 通过 parent_anchor_id 与 (parent_head_fingerprint, covered_turn_chain_hash) 自然形成一棵**只增不改的有向无环前缀树（Prefix DAG/Tree）**：非累计视图轮次不产生假前缀节点，指令切换自动生长出新 parent_head_fingerprint 分支，而后续任意轮次切回原指令或原累计对话视图时，均能精确寻回树上覆盖最长的合法祖先节点并辅以 Multi-turn Delta 无损衔接。

**6.4 向后兼容性设计**

1.  **存量旧 Session 零迁移中断**：已创建的存量 Session 其 session.metadata\["\_relay_route"\] 无 continuation_contract 字段，ContinuationIntentPlanner 自动判定为 disabled，100% 保持原有 gemini_native（generateContent + CachedContent）或 responses（store=False）行为，不改写存量数据库快照。

2.  **历史 Request 幂等重放与恢复兼容**：存量 relay-request/2.1～2.4 请求保留原 request_identity() 哈希公式与 v3 / v89 恢复分支；升级期间 API 与 Worker 同时保留 v89 与 v90 RPC，满足滚动/协同升级兼容性。

3.  **未启用续接的模型透明旁路**：如 Claude Messages、Moonshot ChatCompletions 等未配置 continuation 合同的供应，所有新增规划器与绑定器均以常数时间 disabled 空操作通过，零性能损耗。
