### 2.2 解决 `INTERACTIONS_HISTORY_HEAD` 排除 `instructions`/`tools` 的方案偏离

**偏离定位**：`app/core/continuation_fingerprint.py` 中的 `continuation_head()` 对 `gemini_interactions` 使用 `INTERACTIONS_HISTORY_HEAD`（`relay-continuation-head/3`），故意把 `instructions` 和 `tools` 从头部指纹中剔除。这与《续接改造方案》第 2.5.1 / 4.3 节“修改 `instructions` 或 `tools` 必须触发头部指纹断裂、自动分叉重开新链并携带完整可见历史”的要求直接相悖；若不修正，在多阶段工作流切换不同 `instructions` 或 `tools` 时，仍会错误复用旧 `previous_interaction_id`，不仅导致 Google 服务端前缀 KV Cache 失效，还可能造成新指令与旧链历史角色/工具语义错位。

**修改方法（合同驱动 + 存量兼容）**：

1. **升级头部指纹为合同字段驱动（`relay-continuation-head/4`）**：读取冻结 `continuation_contract.get("head_invariants", ("instructions", "tools", "account_scope_id", "model"))` 决定参与头部哈希的维度。默认情况下，对 `instructions` 做受控空白规整、对 `tools` 调用 `normalize_native_payload({"tools": tools}, response_schemas=True)` 规范化后纳入 `parent_head_fingerprint`，同时严格排除 `thinking`、`effective_options`（`temperature`/`top_p`/`max_output_tokens`）与 `structured_output`。

2. **无损兼容存量 `head/3` 冻结快照**：在 `continuation_head()` 保留 `LEGACY_CONTINUATION_HEAD`（`head/2`）与 `INTERACTIONS_HISTORY_HEAD`（`head/3`）只读分支，新受理请求一律写入 `head_format = "relay-continuation-head/4"`；在途旧请求恢复时仍按其冻结的 `head_format` 复核，避免部署窗口内 `CONTINUATION_CONTEXT_MISMATCH`。

def continuation_head(snapshot: dict[str, Any], *, head_format: str = CONTRACT_DRIVEN_HEAD,
                      head_invariants: tuple[str, ...] = ("instructions", "tools", "account_scope_id", "model")) -> str:
    if head_format in {LEGACY_CONTINUATION_HEAD, INTERACTIONS_HISTORY_HEAD}:
        # 保留存量在途请求只读兼容逻辑
        ...
    if head_format != CONTRACT_DRIVEN_HEAD:
        raise ValueError(f"Unsupported continuation head format: {head_format!r}")
    payload: dict[str, Any] = {
        "format": CONTRACT_DRIVEN_HEAD,
        "session_id": snapshot.get("session_id"),
        "tenant_id": snapshot.get("tenant_id"),
        "conversation_hash": snapshot.get("conversation_hash"),
        "connection_id": snapshot.get("connection_id"),
        "account_scope_id": snapshot.get("account_scope_id"),
        "connection_spec_hash": snapshot.get("connection_spec_hash"),
        "protocol_profile_hash": snapshot.get("protocol_profile_hash"),
        "model": snapshot.get("model"),
        "upstream_model": snapshot.get("upstream_model"),
        "protocol": snapshot.get("protocol"),
    }
    if "instructions" in head_invariants:
        inst = snapshot.get("instructions")
        payload["instructions"] = inst.strip() if isinstance(inst, str) else inst
    if "tools" in head_invariants:
        tools = snapshot.get("tools") or (snapshot.get("provider_payload") or {}).get("tools")
        payload["tools"] = normalize_native_payload({"tools": tools}, response_schemas=True).get("tools") if tools else None
    return stable_hash(payload)

### 2.3 补齐 `require_stateful_anchor`、ZDR Fail-Closed 门禁与计划持久化

**缺口定位**：`plan_frozen_context()` 当前仅区分 `off` 与 `auto`，不支持 `prefer_stateful_anchor` / `require_stateful_anchor` 策略，遇到 ZDR（零数据保留）时仅静默回退为 `off` 而不报错；`request_acceptor.py` 虽然把 `continuation-plan.json` 存入了对象存储，但未将 `continuation_plan_object_id` 和 `continuation_plan_hash` 传给 `repo.accept_request_v3()` 落库；同时 `continuation_topology` 是在 `build_context_plan()` 返回后由 `request_acceptor.py` 事后拼接并覆盖 `context_plan_hash`，破坏了 `ContextPlanner` 的内聚性。

**修改方法**：

1. **引入 `ContinuationDecisionError` 与 ZDR / `require` 门禁**：在 `app/shared_contracts.py`（或 `app/execution_plane/continuation_contracts.py`）定义 `ContinuationDecisionError(code, message)`，在 `request_acceptor.py` 捕获并映射为 HTTP 409/422。在 `plan_frozen_context()` 中：

   * 识别有效策略 `effective_mode`（`off` / `prefer_stateful_anchor` / `require_stateful_anchor`）；若 `policy.allow_request_override is False` 但调用方传入了不同的 `body_mode`，直接拒绝。

   * 若租户或合同开启 `zero_data_retention=True` 且 `contract.requires_upstream_store=True`、`forbid_when_zero_retention=True`：在 `require_stateful_anchor` 下抛 `ContinuationDecisionError("CONTINUATION_FORBIDDEN_BY_ZDR_POLICY")`；在 `prefer_stateful_anchor` 下确定性返回 `disabled`（`decision_reason="zdr_forbidden"`）。

   * 在 `require_stateful_anchor` 下，若供应未通过认证（`verification_status != "verified"`）、`anchor_class == "none"` 或与本轮显式请求的缓存机制互斥，同样直接 Fail-Closed 拒绝受理。

2. **收口 `ContextPlanner` 职责**：将 `continuation_topology`（`parent_head_fingerprint`、`visible_turn_count`、`turn_prefix_chain`）的计算下沉至 `context_planner.py` 的 `build_context_plan()` 内部，一次性计算 `context_plan_hash`，消除 `request_acceptor.py` 事后篡改并重算哈希的补丁写法。

3. **落库 `continuation_plan_object_id` 与 `continuation_plan_hash`**：扩展 `repo.accept_request_v3()` 与对应数据库 RPC，使 `continuation-plan.json` 的对象引用与哈希随 Request 事务原子落库，支持独立审计与 `PlanLoader` 校验。

### 2.4 收口 `ResultCommitter` 脏写入与泛化 `recover_and_commit()` 门禁

**缺口定位**：`app/execution_plane/result_committer.py` 的 `finalize()` 在 `elif not is_interactions` 分支对所有 `c_mode != "off"` 的非 Interactions 请求都构造并写入 `v1` `ContinuationAnchorRecord`，导致普通无状态协议也在往 `relay_continuation_anchors` 写无意义记录；此外，`recover_and_commit()` 中关于 `row.get("sealed_continuation_binding") != binding` 和 `prepared_payload_hash != seal_hash` 的数据库封存核验被硬编码限制在 `protocol == "gemini_interactions"` 下。

**修改方法**：

1. **删除 `finalize()` 中的 `elif not is_interactions` 脏写入分支**：统一仅当 `continuation_plan.schema_version == "relay-continuation-plan/2"`、`topology["reusable_on_commit"] is True`、`actual_binding["store_upstream_state"] is True` 且 `effective_policy == "conversation"`、历史成功落盘时，才进入通用锚点组装方法 `_build_committed_anchor()`。

2. **通用化观测核验与锚点凭证组装**：在 `_build_committed_anchor()` 中，依据 `protocol_profile["continuation"]` 核验上游状态落盘事实（如 `observed.get("upstream_state_stored") is True`，兼容既有 `interaction_stored`）以及 `observed.get("previous_anchor_ref") == actual_binding.get("upstream_handle")`，并补充写入 `anchor_class`、`affinity_epoch`、`is_root_prefix=True`、`covered_materials_digest` 等完整字段，交由 `complete_continuation_context_v91` 原子落库。

3. **对全部 `v2` 续接协议统一开启 `recover_and_commit()` 封存复核**：去掉 `recover_and_commit()` 中的 `protocol == "gemini_interactions"` 限制，只要请求为 `relay-continuation-plan/2` 且 `binding["effective_mode"] != "disabled"`，恢复路径一律强制比对 `execution-fact.json` 的 `continuation_execution_binding` 与数据库 `relay_requests.sealed_continuation_binding` 及 `prepared_payload_hash` 一致性。

### 3.1 新增独立合同模块 `app/control_plane/continuation_contracts.py` 与 `ContinuationPolicySpec`

**缺口定位**：仓库缺失方案 2.2 / 3.1 节定义的 `app/control_plane/continuation_contracts.py`，无 `ContinuationCapabilityContract`、`ContinuationPolicySpec` 与 `validate_continuation_cross_contract()`；`ModelOffering` 缺少 `continuation_policy_id`；`app/control_plane/governance/workbook.py` 采用手写硬编码字典为 `gemini_interactions` 拼装 `continuation_contract`，极易出现字段漂移。

**修改方法**：

1. **新建 `app/control_plane/continuation_contracts.py`**：

   * 定义不可变数据类 `ContinuationCapabilityContract`（字段严格对齐方案 2.2 节：`anchor_class`、`verification_status`、`supports_branching`、`supports_multiturn_delta`、`requires_upstream_store`、`forbid_when_zero_retention`、`mutually_exclusive_cache_mechanisms`、`retention_ttl_seconds`、`anchor_safety_margin_seconds`、`head_invariants`、`re_specify_head_on_delta`、`requires_thought_signature_on_replay`、`max_delta_turns`）与 `ContinuationPolicySpec`（含 `policy_id`、`revision`、`default_mode`、`allow_request_override`、`allow_stateless_fallback_pre_dispatch`、`allow_head_mismatch_reopen`、`invalidate_on_affinity_rotation`、`max_active_anchors_per_session`）。

   * 定义注册表常量 `IMPLEMENTED_CONTINUATION_PROTOCOLS = frozenset({"gemini_interactions", "responses"})`（灰度阶段可先仅放开 `gemini_interactions`，待 Responses 修复 `previous_response_id` 与 `store` Bug 后再加入）。

   * 实现核心编译期校验函数 `validate_continuation_cross_contract(connection, capability, profile, policy)`，在离线编译与启动加载阶段执行全部静态门禁。

2. **扩展 `ModelControlPlane` 与 `ModelOffering`**：在 `app/control_plane/definitions.py` 中为 `ModelControlPlane` 增加 `continuation_policies` 集合、`_continuation_policy_from_mapping()` 解析器与 `continuation_policy(policy_id)` 查询方法，并在 `ModelOffering` 增加可选字段 `continuation_policy_id: str | None = None`。

3. **改造 `workbook.py` 消除硬编码字典**：让 `workbook.py` 通过 `ContinuationCapabilityContract(...).canonical()` 构造续接合同，并支持从工作簿或声明文件绑定 `continuation_policy_id`。

Python

```
# app/control_plane/continuation_contracts.py（核心交叉校验门禁示意）
IMPLEMENTED_CONTINUATION_PROTOCOLS = frozenset({"gemini_interactions"})
VALID_ANCHOR_CLASSES = frozenset({"none", "immutable_tree_anchor", "linear_ephemeral_cursor", "mutable_session_container"})

def validate_continuation_cross_contract(
    *, connection: Any, capability: Any, profile: Any, policy: Any | None,
) -> None:
    cont = capability.continuation or {}
    anchor_class = str(cont.get("anchor_class") or "none")
    if anchor_class not in VALID_ANCHOR_CLASSES:
        raise ValueError(f"Unknown continuation anchor_class: {anchor_class!r}")
    if anchor_class in {"linear_ephemeral_cursor", "mutable_session_container"} and cont.get("supports_branching") is True:
        raise ValueError(f"{anchor_class} cannot declare supports_branching=True")

    default_mode = getattr(policy, "default_mode", "off") if policy is not None else "off"
    if default_mode != "off" or anchor_class != "none":
        if connection.protocol not in IMPLEMENTED_CONTINUATION_PROTOCOLS:
            raise ValueError(f"Protocol {connection.protocol!r} has no certified continuation implementation")
        if profile is None or not (profile.continuation or {}).get("request_anchor_field"):
            raise ValueError(f"Protocol profile for {connection.protocol!r} lacks continuation wire mapping")
        profile_class = (profile.continuation or {}).get("anchor_class")
        if profile_class and profile_class != anchor_class:
            raise ValueError("Capability and protocol profile disagree on continuation anchor_class")

    # 显式缓存互斥门禁（例如 Gemini Interactions 严禁同时开启 stateful_resource）
    exclusive = set(cont.get("mutually_exclusive_cache_mechanisms") or ())
    if connection.protocol == "gemini_interactions":
        exclusive.add("stateful_resource")
    cap_cache = set((capability.cache or {}).get("supported_mechanisms") or ())
    prof_cache = set((profile.cache or {}).get("supported_mechanisms") or ()) if profile else set()
    if exclusive & (cap_cache | prof_cache):
        raise ValueError(f"Continuation mutually exclusive cache mechanisms enabled: {sorted(exclusive & (cap_cache | prof_cache))}")

    # ZDR 零数据保留静态门禁
    zdr = bool((connection.metadata or {}).get("zero_data_retention") or (capability.metadata or {}).get("zero_data_retention"))
    if zdr and default_mode == "require_stateful_anchor" and cont.get("requires_upstream_store", True):
        raise ValueError("CONTINUATION_FORBIDDEN_BY_ZDR_POLICY: ZDR supply cannot require upstream stateful anchor")
```
